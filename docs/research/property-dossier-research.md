# Property dossier and private ownership documents — research

Research for two proposed features, done **before** any code is written:

- **Feature A — private ownership documents.** An owner attaches proof-of-ownership files when
  submitting a property. Only that owner and Aqarat staff may see them. `property_photo` is
  untouched; this is a separate, private channel.
- **Feature B — the property dossier.** One read-only panel showing everything the system knows
  about one property: owner, timestamps, status, private documents, valuation history, viewings,
  reservations, contracts, payments, audit trail.

Sections 1 is codebase fact, cited as `file.java:line`. Section 2 is external research, cited by
URL. Section 3 is the synthesis, and it is the only part that proposes anything.

This document does not decide anything. `docs/DESIGN.md` and `docs/DECISIONS.md` remain the
authority. It builds directly on [`marketplace-domain-research.md`](marketplace-domain-research.md),
whose §1.5 already establishes what a Lebanese and Jordanian title deed contains as data and whose
§1.6 already lists deed upload as a NICE-TO-HAVE — this document is the detail behind that line.

## 1.1 How a `property_photo` file is handled today, end to end

Five classes and one table. The convention is small and consistent, and Feature A should mirror it
rather than invent a second one.

**Step 1 — the controller picks files.**

`SubmitPropertyController.java:580-597` — `handleAddPhotos()`:

```java
FileChooser chooser = new FileChooser();
chooser.setTitle("Choose property photos");
chooser.getExtensionFilters().add(
    new FileChooser.ExtensionFilter("Images (*.jpg, *.jpeg, *.png)", "*.jpg", "*.jpeg", "*.png"));
List<File> chosen = chooser.showOpenMultipleDialog(null);
```

The chosen `File`s become `Path`s in a controller-local `selectedPhotos` list, capped at 8
(`SubmitPropertyController.java:592`). `MyPropertiesController.java:176-199` has the same
`FileChooser` for adding photos to an existing property, **with no cap**.

**Step 2 — the paths are wrapped in a model that carries nothing else.**

`model/NewPhoto.java:5-16` is a single final `Path` with a getter. No name, no size, no bytes.
`SubmitPropertyController.java:562-565` builds the list; `MyPropertiesController.java:185-187`
does the same.

**Step 3 — the service opens the transaction and calls the store.**

`PropertyService.java:106-133` — `submit(Property, List<NewPhoto>)`:

```java

int sortOrder = 0;
for (NewPhoto photo : photos) {
    String filePath = PhotoStore.store(id, sortOrder, photo.getPath());
    PropertyPhoto record = new PropertyPhoto();

auditService.record(connection, "property", id, "CREATE", null, PropertyStatus.PENDING_REVIEW.name());
```

`catch (SQLException | IOException e) { connection.rollback(); throw e; }` at
`PropertyService.java:127-130`. `addPhotos(int, List<NewPhoto>)` at `PropertyService.java:140-168`
is the same shape for an existing property, with `sortOrder` seeded from the existing photo count.

**Step 4 — the copy lands on disk.**

`util/PhotoStore.java` is the whole storage layer, 41 lines:

```java
private static final Path UPLOADS_DIR = Path.of("uploads");           // :10
private static final Path IMAGES_DIR = UPLOADS_DIR.resolve("images"); // :11

public static String store(int propertyId, int index, Path source) throws IOException {  // :23
    Files.createDirectories(IMAGES_DIR);
    String extension = extension(source);
    String filename = "p" + propertyId + "-" + index + "." + extension;
    Files.copy(source, IMAGES_DIR.resolve(filename), StandardCopyOption.REPLACE_EXISTING);
    return "images/" + filename;                                       // :28
}
```

**The exact convention, stated plainly:**

| Fact | Value |
|---|---|
| Root | `Path.of("uploads")` — **relative**, resolved against the JVM working directory (`PhotoStore.java:10`) |
| On-disk path | `uploads/images/p{propertyId}-{sortOrder}.{jpg\|png}` |
| Stored in the database | the path **relative to the uploads root**, e.g. `images/p42-0.jpg` (`PhotoStore.java:28`) |
| Filename source | **generated by the application**, never the user's (`PhotoStore.java:26`) |
| Collision behaviour | `REPLACE_EXISTING`, made safe by the property id + index in the name |

**Step 5 — reading it back.** Every read-side call re-joins the root by hand. There are five
places and they do not agree on how:

| File:line | Expression |
|---|---|
| `PropertyDetailsController.java:60, 238` | `private static final String IMAGE_ROOT = "uploads";` then `Path.of(IMAGE_ROOT, photo.getFilePath())` |
| `PropertyDetailsController.java:271` | `Path.of(IMAGE_ROOT, photo.getFilePath())` in `setMainPhoto` |
| `ReviewSubmissionController.java:63` | its own copy of `IMAGE_ROOT = "uploads"` |
| `UIHelper.java:85, 184, 422` | `new File("uploads/" + photoPath)` — string concatenation, three times |
| `MyPropertiesController.java:270` | `new File("uploads/" + path)` |

All of them guard with `file.exists()` / `Files.exists(path)` and fall back to a placeholder.
Then `new Image(file.toURI().toString(), w, h, ...)`.

`db/schema.sql:146-157` — `property_photo` holds `file_path VARCHAR(300) NOT NULL`,
`is_primary BIT`, `sort_order INT`, FK to `property` with `ON DELETE CASCADE`.
`dao/PropertyPhotoDao.java:15-33` (`findByProperty`), `:41-58` (`insert`), `:60-66` (`delete` —
**never called from anywhere**; grep for `propertyPhotoDao.delete` returns nothing).

**Two loose ends worth knowing before mirroring this:**

1. `config/local.properties` declares `storage.images=uploads/images` and
   `storage.proofs=uploads/proofs`, and so does `config/local.properties.example`. **Neither key
   is ever read.** `Config.get`/`Config.require` are called only with `db.*` and `ai.*` keys
   (`Db.java:25-29`, `ChatClient.java:37-59`). `PhotoStore` hardcodes the path instead. The
   `uploads/proofs/` directory exists on disk and is empty; `.gitignore` lists `proofs/`;
   `db/seed.sql:656` seeds one `payment.proof_path` of `'proofs/placeholder.pdf'`. So a private
   file channel was *planned* and never wired.
2. `payment.proof_path VARCHAR(300)` (`db/schema.sql:298`) is today a **free-text field**, not an
   upload. `MyContractsController.java:314, 321` — a `TextField` with the prompt
   "Transfer slip number, or a path to the file"; `PaymentsController.java:500-501` renders it as
   a label. No file is ever copied. Feature A's uploader would be the first real one after photos.

## 1.2 Existing file validation on photo upload

There is one check, and it is an extension suffix test on the *source* filename:

`util/PhotoStore.java:31-40`:

```java
private static String extension(Path source) throws IOException {
    String name = source.getFileName().toString().toLowerCase();
    if (name.endsWith(".jpg") || name.endsWith(".jpeg")) { return "jpg"; }
    if (name.endsWith(".png")) { return "png"; }
    throw new IOException("Only JPG or PNG photos are accepted.");
}
```

That is the entirety of it. Stated plainly, there is **no**:

- content or magic-number sniffing — a renamed `.exe` called `x.jpg` is copied happily;
- size cap of any kind, at any layer;
- count cap outside `SubmitPropertyController.java:592` (`MyPropertiesController` has none);
- filename sanitisation — and **none is needed**, because `PhotoStore.java:26` generates the
  stored name from the property id and index and never uses the user's name. This is already the
  correct behaviour by OWASP's rule (§2.3); it just happens for free rather than on purpose.

The `FileChooser` extension filter (`SubmitPropertyController.java:584-585`) is a convenience in
the picker dialog, not a control — the user can switch it to "All files".

Where this matters for Feature A: an ID scan is a PDF as often as an image, so the allow-list
grows; and a document is a file the agency will be asked to produce later, so a truncated or
corrupt copy is worse than a rejected upload.

## 1.4 How authorisation is actually enforced today

**There is no `hasPermission` helper.** `docs/DECISIONS.md` §9 says the chosen design was "a `role`
column on the user and a small `hasPermission` helper"; the helper was never written. What exists
is `util/SessionManager.java`, 36 lines:

```java
public static AppUser getCurrentUser()  // :21
public static boolean isAdmin()         // :25  currentUser != null && role == Role.ADMIN
public static boolean isAgent()         // :29
public static boolean isCustomer()      // :33
```

Enforcement is two things layered, and both matter for Feature A.

**(a) The controller gates the whole panel by role.** Concrete examples:

- `MyContractsController.java:85-89` — `if (user == null || user.getRole() != Role.CUSTOMER) { denyAccess(); return; }`, where `denyAccess()` (`:94-101`) hides `contentBox` and shows `accessDeniedLabel`.
- `PortfolioController.java:106-107` — `if (user == null || !SessionManager.isCustomer())`.
- `PropertyDetailsController.java:188-190` — ownership, not role:
  ```java
  boolean isOwner = isCustomer && SessionManager.getCurrentUser() != null
      && SessionManager.getCurrentUser().getId() == property.getOwnerId();
  ```
  and `:191-192` uses it to decide whether the viewing/reserve actions render at all.

**(b) The service binds the user id into the query.** This is the pattern CONVENTIONS.md and
`DESIGN.md` §8 describe, and the code says so out loud:

`ContractService.java:59-66`:

```java
// clientId is bound into the query rather than filtered afterwards, so a
// client can only ever be handed their own contracts (DESIGN.md section 8).
public List<Contract> findByClient(int clientId) throws SQLException {
    try (Connection connection = Db.get()) {
        return contractDao.findByClient(connection, clientId);
    }
}
```

`ContractDao.java:95-112`:

```java
// A client sees only their own contracts - client_id is bound into the
// WHERE clause here, not applied by filtering a full result set
// afterwards (DESIGN.md section 8).
public List<Contract> findByClient(Connection connection, int clientId) throws SQLException {
    String sql = ("""
        SELECT %s
        FROM contract
        WHERE client_id = ?
        ORDER BY created_at DESC
        """).formatted(COLUMNS);
```

Same shape at `ReservationDao.java:95-114` (`findByClient`), `ViewingDao.java:88-107`,
`PropertyDao` via `PropertyService.findByOwner(int)` (`PropertyService.java:81`). And
`PropertyService.searchPublished` (`:53`) hard-wires the status in Java rather than accepting it
as a parameter, with the comment at `:71-73`: "Passing the status here, rather than letting a
caller choose it, is what keeps a draft or a rejected submission from ever reaching a public
screen."

**The gap Feature A has to close.** Every scoped read today is scoped by *the id the controller
passes*, and no service verifies that the id belongs to the signed-in user. `findByClient(7)` will
return user 7's contracts to anyone who calls it. That is fine while the only caller is a
controller that got the id from `SessionManager` — but a private-document read must not depend on
the caller being polite. Feature A's read should take the *requesting user* rather than an id, and
choose its query from that user's role, so the check cannot be skipped by calling the method
differently. Section 3.3 spells that out.

# 2. External research

## 2.1 What documents actually prove ownership and authority to sell

`marketplace-domain-research.md` §1.5 already establishes the registry side: Lebanon's
Directorate General of Land Registry and Cadastre keeps ownership, plot and building
specifications and outstanding disputes across 17 offices, addressed
governorate → registry office → zone/section → lot/parcel. That is not repeated here. What
follows is the **document** side — the paper an owner would actually hand an agency.

**Lebanon — the title document has two accepted forms, and the consulates name both.**
The Embassy of Lebanon's consular page for a power of attorney affecting real estate requires
"a copy of the deed of property or a registry certificate (افادة عقارية أو سند ملكية)"
([Embassy of Lebanon — Power of Attorney](https://www.lebanonembassyus.org/consular-services/power-of-attorney/)).
So:

- **سند ملكية / *sanad milkiyye*** — the title deed itself.
- **افادة عقارية / *ifada 3akariyya*** — the land-registry certificate or extract. In practice
  this is the one requested, because it is current: it is issued on demand and reflects the
  register today rather than on the day the deed was cut.

The registry extract shows registered ownership, surface area and property identification, and it
reveals charges — "mortgages, privileges, attachments, litigation notices, and easements"
([Kallas Law Firm — buying property in Lebanon](https://www.klfi.net/blog-buying-property-lebanon-en/)).
That last point is the one worth carrying into a student project's documentation: a title document
is not only proof of who owns a thing, it is proof of *what is attached to it*.

**Ownership passes by notarial deed and inscription, not by the power of attorney.** The same
source is emphatic that the act that transfers ownership is the authentic deed executed before a
notary and inscribed at the registry; the power of attorney merely lets someone execute it, and
is "frequently misused as a substitute". A sales agreement is signed before a notary public who
verifies legality and authenticity
([Obeid & Medawar](https://www.omlfirm.com/2023/12/12/real-estate-transactions-in-lebanon/), *snippet*).

**Power of attorney — what it carries as data.** For a real-estate POA the Lebanese consulate
requires the principal's original ID (identity card, passport or civil registration document), a
copy of the recipient's ID, a copy of the property document, and "the number and location of the
property … clearly mentioned"; the notary seals it beside the principal's signature and it is
signed by two witnesses
([Embassy of Lebanon](https://www.lebanonembassyus.org/consular-services/power-of-attorney/)).
So a POA is inherently *scoped to a named property* — which is exactly why it belongs on a
`property_document` row rather than on the user record.

**Agency mandate / authority to sell.** The named instrument in the Anglophone market is the
**listing agreement**: NAR defines it as "a contract between you and your agent that says the
agent can represent you and market your property to potential buyers and their agents and
establishes the sales price for your home", and names four arrangements — **exclusive
right-to-sell** (one agent, compensated no matter who sells), **exclusive agency** (one agent, but
the owner may sell it themselves without owing compensation), **limited-service**, and
**non-exclusive** ([NAR — Consumer Guide: Listing Agreements](https://www.nar.realtor/the-facts/consumer-guide-listing-agreements)).
MLS rules add the operative detail: "The listing agreement must include the seller's written
authorization to submit the agreement to the multiple listing service"
([NAR MLS model rules](https://www.nar.realtor/handbook-on-multiple-listing-policy/c-model-rules-and-regulations-for-an-mls-operated-as-a-committee-of-an-association-of-realtors), *snippet*).
The generalisable fact for Aqarat: **publishing someone else's property requires a signed,
time-bounded, written authorisation.** That is precisely the document Aqarat has no place to put
today.

**Inheritance / succession.** In Lebanon the operative document is the **probate decision,
قرار حصر الإرث (*hasr irth*)**, which "establishes the death and identifies the heirs and their
shares", issued by the single civil judge for Christian sects and by the competent religious
court for Islamic sects; a valid inheritance decision is required before inherited property can
be registered to the heirs
([Kallas Law Firm — probate and inheritance](https://www.klfi.net/probates-inheritance-and-asset-transfer-process-in-lebanon/), *snippet*;
[Lebanese Inheritance Law — transferring real estate to heirs](https://www.lebaneseinheritancelaw.com/inheritance-law/2734099_transferring-real-estate-to-the-heirs), *snippet*).
This confirms `marketplace-domain-research.md` §1.5's warning from a second direction:
**ownership is a set with shares, not a single `owner_id`** — a *hasr irth* names several people
and their fractions.

**National ID.** Every one of the above requires an identity document alongside it, and the
consulate accepts "identity card, passport, or civil registration document"
([Embassy of Lebanon](https://www.lebanonembassyus.org/consular-services/power-of-attorney/)).
`marketplace-domain-research.md` §5.4 already reached the honest student-project conclusion:
a national ID field plus a "verified by agent" flag is the 5% of KYC that costs nothing.

**A defensible short enum.** Five constants, each with a real-world referent named above, none
speculative:

| Constant | Real-world document | Why it earns a slot |
|---|---|---|
| `TITLE_DEED` | سند ملكية / افادة عقارية; Jordan's *koushan*/*sanad tasjeel* | The primary proof. Covers both the deed and the registry extract — distinguishing them is a lawyer's problem, not a student schema's. |
| `NATIONAL_ID` | Identity card, passport, civil registration record | Required alongside every other document. Also the most sensitive thing in the system (§2.4). |
| `AGENCY_MANDATE` | Listing agreement / authority to sell | The document that makes publication lawful. |
| `POWER_OF_ATTORNEY` | Notarised POA, two witnesses, property named | The case where the person submitting is not the person on the deed. |
| `INHERITANCE_DEED` | قرار حصر الإرث / probate decision | The other case where the submitter is not the person on the deed. Names heirs and shares. |
| `OTHER` | — | The escape hatch. Without it the enum is a lie the first time someone has a survey plan. |

Six with `OTHER`. Resist adding `MORTGAGE_RELEASE`, `SURVEY_PLAN`, `TAX_CLEARANCE` — each is real,
none changes a screen, and `OTHER` plus the `note` column absorbs all of them.

## 2.2 Storing sensitive files: filesystem-plus-path vs. database BLOB

**What Microsoft says.** SQL Server offers three ways, and Microsoft states the decision rule
in one paragraph. FILESTREAM "enables SQL Server-based applications to store unstructured data,
such as documents and images, on the file system … at the same time maintain transactional
consistency between the unstructured data and corresponding structured data". Use it when:

> - Objects that are being stored are, on average, larger than 1 MB.
> - Fast read access is important.
> - You're developing applications that use a middle tier for application logic.
>
> For smaller objects, storing **varbinary(max)** BLOBs in the database often provides better
> streaming performance.
>
> — [FILESTREAM (SQL Server), Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/blob/filestream-sql-server?view=sql-server-ver17)

The costs Microsoft lists on the same page and that matter here: FILESTREAM "isn't automatically
enabled when you install or upgrade SQL Server" — it needs Configuration Manager plus a special
filegroup plus a table change; it applies to **SQL Server on Windows** only; "Encryption isn't
supported on FILESTREAM data"; "SQL logins will not work with FILESTREAM containers. Only NTFS or
ReFS authentication will work"; and the container is a folder SQL Server manages, with an explicit
warning not to add or remove files in it by hand.

**FileTable** builds on FILESTREAM and exposes the files through a Windows share so ordinary
Windows applications see them as a normal folder; every row is a file or a directory, with
`file_stream`, `path_locator`, and ten file attributes
([FileTables (SQL Server), Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/blob/filetables-sql-server?view=sql-server-ver17)).
Note what that means for a *private* document store: FileTable's whole selling point is
**non-transactional access through a Windows share** — it makes the files *more* reachable outside
the application, not less. It is the wrong direction for this feature even before the setup cost.

**What is right for this project, and why.** Filesystem-plus-path, mirroring `PhotoStore`. The
reasoning, in order of weight:

1. **The pattern already exists and works** (§1.1). A second storage mechanism in a 75-class
   project would be the exact "architecture for its own sake" `DESIGN.md` §12 forbids. Rung 2 of
   the ladder: reuse what is there.
2. **The setup cost is not zero and lands on the grader.** `docs/DECISIONS.md` §12 chose local
   SQL Server with committed `schema.sql`/`seed.sql` specifically so "anyone can stand the system
   up in two minutes and nothing can fail in front of the class". FILESTREAM requires enabling a
   feature in SQL Server Configuration Manager, which `schema.sql` cannot do — it would break that
   guarantee for a feature nobody is grading.
3. **Sizes sit under Microsoft's own threshold.** A phone photo of a deed or an ID is 0.5–5 MB;
   a scanned PDF a little more. That straddles the 1 MB line, so FILESTREAM's advantage is not
   even clearly present.
4. `varbinary(max)` in the row is the *tempting* answer here, because it makes the access control
   real (see below) and because a delete of the property deletes the bytes with it, transactionally.
   It is a legitimate choice and the trade is honest. It is rejected only because it means a second
   upload/download path and a second set of bugs in a two-week budget — not because it is wrong.

**The hole in the filesystem approach, stated without hedging.**

**A file path in a database is not an access control.** `property_document.file_path` records
*where* a file is. It does not stop anyone from opening `uploads/documents/` in File Explorer and
reading every national ID in the system. The application's permission check governs the
application's own UI and nothing else. Concretely, in this project today, the following are all
true at once:

- the database enforces referential integrity on the path but has no opinion about the bytes;
- the app can refuse to render a document to a guest, and that refusal is real *inside the app*;
- any user of the machine — including the guest, if it is a shared demo laptop — can read every
  file in the folder with no application involved at all.

The mitigations that actually exist at this scale are ordered, and only the first two are free:

1. **Do not put the folder anywhere a web server or a share could expose it.** OWASP's own storage
   ranking is: a different host, then "outside the webroot, where only administrative access is
   allowed", then inside the webroot as a last resort
   ([OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)).
   A desktop app has no webroot, which removes the worst case for free but does not create a
   control.
2. **Say so in the README.** A documented limitation is a design decision. An undocumented one is
   a bug the examiner finds.
3. NTFS ACLs on `uploads/documents/` — real, but machine-specific, not expressible in
   `schema.sql`, and it breaks the two-minute setup.
4. Encrypting the bytes at rest with a key held by the app — real, and roughly a day of work
   including key handling, which is a day not spent on the dossier.
5. `varbinary(max)` — the only option where the database's own `GRANT` is the control.

The recommended answer for this project is **1 + 2**: mirror `PhotoStore`, and write one honest
paragraph in the README saying that documents are stored on the local filesystem, that the
application's permission check governs the application only, and that a production deployment
would move them behind a service or into `varbinary(max)`. That sentence costs nothing and is
worth more in a viva than an encryption scheme that half-works.

## 2.3 File validation

OWASP's File Upload Cheat Sheet is the primary source and its rules map cleanly onto what
`PhotoStore` does and does not do.

**Extension allow-list, not deny-list.** "Ensure the usage of *business-critical* extensions only,
without allowing any type of *non-required* extensions." A deny-list is explicitly weaker —
"blocking specific extensions is a weak protection method on its own". Applications that check
extensions must also "validate the full filename to prevent any bypass" — double extensions
(`.jpg.php`) and null-byte tricks (`.php\0.jpg`) are the named bypasses
([OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)).

**Content sniffing on top of the extension.** The `Content-Type` header "cannot be trusted, as it
is trivial to spoof"; validate the file signature. But OWASP is careful that magic-byte checking
"should not be used on its own" — it is a layer, not the answer. In a JavaFX desktop app there is
no `Content-Type` at all, so the practical version is: read the first bytes of the chosen file and
require one of the signatures for the formats you accept.

| Format | First bytes |
|---|---|
| JPEG | `FF D8 FF` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| PDF | `25 50 44 46` (`%PDF`) |

That is one ~15-line helper. It catches the realistic case for this project — a student demoing
with a renamed file, or an owner attaching the wrong thing — and it is the difference between "we
check the extension" and "we check the file", which is a sentence worth being able to say.

**Server-generated filenames.** "Creating a random string as a filename, such as generating a
UUID/GUID, is essential." If a user-supplied name must be kept, OWASP requires a maximum length
based on filesystem constraints, restriction to "alphanumeric characters, hyphen, spaces, and
periods", and blocking leading periods (hidden files), sequential periods (directory traversal)
and leading hyphens or spaces.

**Aqarat already does the right thing here and should keep doing it.** `PhotoStore.java:26` builds
`p{propertyId}-{index}.{ext}` and never touches the user's name. Mirroring that for documents
(`d{propertyId}-{n}.{ext}`) makes every one of these attacks structurally impossible rather than
filtered: there is no user string in the path, so there is nothing to traverse with. The *original*
filename can still be stored as **data** in a column and displayed as a label — a stored string is
not a path.

The Windows-specific traps only matter if a user-supplied name is ever used as a filename.
Microsoft's list, for completeness: the reserved characters `< > : " / \ | ? *`, integer value zero
(the ASCII NUL), characters 1–31; the reserved device names CON, PRN, AUX, NUL, COM1–COM9,
LPT1–LPT9 — and "avoid these names followed immediately by an extension; for example, NUL.txt and
NUL.tar.gz are both equivalent to NUL"; "do not end a file or directory name with a space or a
period"; and MAX_PATH of 260 characters before Windows 10 1607
([Naming Files, Paths, and Namespaces, Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)).
**Aqarat needs none of these checks** as long as it keeps generating names. That is the whole
argument for generating them.

**Size cap.** "The application should set proper size limits for the upload service." There is no
cap anywhere in Aqarat today (§1.2). A cap is one `Files.size(path) > MAX` comparison before the
copy, and for scanned documents 10 MB is generous. Skipping it means one 4 GB video fills the
demo machine's disk during marking.

## 2.4 PII and retention for ID scans

A scan of a national ID is the most sensitive object this system would ever hold — more so than
the payment records, because an ID copy is directly reusable for impersonation.

**The principle.** GDPR Article 5(1)(c), data minimisation: personal data shall be "adequate,
relevant and limited to what is necessary in relation to the purposes for which they are
processed". Article 5(1)(e), storage limitation: "kept in a form which permits identification of
data subjects for no longer than is necessary for the purposes for which the personal data are
processed" ([GDPR Article 5](https://gdpr-info.eu/art-5-gdpr/)). The UK regulator's gloss is that
the law does not name a period — the controller must set retention periods or review criteria,
justify them per category of data, and delete or anonymise when the period ends
([ICO — storage limitation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/), *snippet* — the ICO returns HTTP 403 to automated fetching).

**What a real platform actually does.** Stripe Identity is the clearest first-party statement,
and it is worth quoting in full because it is three separate practices in one sentence:

> Document and face images are very sensitive and some countries, such as Germany, have laws
> prohibiting ID Document images from being shared or kept longer than necessary. As much as
> possible, access image content with short-lived FileLinks, don't make copies of the file
> contents, and redact sessions and collected images when you're done using them for the purpose
> collected.
>
> — [Stripe — Access verification results](https://docs.stripe.com/identity/access-verification-results)

The mechanics around it are as instructive as the sentence. Access to document images requires a
*restricted* API key, not the ordinary secret key, and by default such a key can read sensitive
results only for the last 48 hours. Links to the image files "must expire within 30 seconds", and
Stripe recommends not downloading the contents onto your own server at all. Redaction is
irreversible and cascades to every related object, with the personal fields replaced by
`[redacted]`. The non-sensitive *outcome* — `status`, `verified_outputs.first_name`, the document
type, the issuing country — stays readable with an ordinary key.

**That is the pattern to steal, and the honest version of it is not a compliance regime.** The
generalisable shape is: **the verification decision outlives the document.** Real platforms keep
"an agent checked this on 3 March and it was valid" permanently, and treat the scan itself as
something to be disposed of once it has done its job.

**What a student project can honestly write in its documentation.** The claim to make is narrow
and true:

- The system records **who verified a document, and when** — so removing the file later does not
  erase the fact that the check happened.
- Documents are visible only to the uploading owner and to staff, enforced in the service layer.
- A staff member can delete a document once it has been verified, and the verification record
  survives it.
- The known limitation is stated plainly: the files live on the local filesystem and the
  application's check governs the application only (§2.2).

The claim **not** to make is any of "GDPR compliant", "encrypted at rest", "retention policy
enforced", or "automatic deletion after N days". A `DELETE` button plus a verification record is
a defensible, honest 5%. A retention scheduler is also the thing `docs/DECISIONS.md` §19 already
refused on different grounds — nothing in this system runs on a timer, and adding one here would
contradict a decision made twice.

## 2.5 The dossier pattern — what it is called and what goes on it

It has a name, several in fact, and they are worth using because they signal the design was
recognised rather than invented.

**"Record page" is the CRM term.** Salesforce's Lightning record page has a fixed anatomy: a
**Highlights Panel** at the top (the key fields, governed by a Compact Layout), then a **Path**
component for lifecycle stage, then a **Tabs** component containing Details (a Record Detail
component), Activity (the Activities component), and Related (Related Lists), with Chatter lower
down ([Trailhead — Custom Record Pages](https://trailhead.salesforce.com/content/learn/modules/lightning_app_builder/lightning_app_builder_recordpage)).
The suggested tab order in Salesforce's own worked example is **Details, Activity, Related**.

**HubSpot lands on a three-column version of the same idea.** A record has "the left sidebar,
middle column, and right sidebar": the left carries actions and property cards, the middle carries
tabs — "a timeline of activities, an overview of the record's associations and important
properties, and custom tabs" — and the right carries "previews of associated records and
attachments" ([HubSpot — Understand and use the record page layout](https://knowledge.hubspot.com/records/work-with-records), *snippet*).
Note where attachments sit: alongside the record, previewed, not buried.

**"Activity timeline" is the name for the chronological strip**, and Salesforce states its purpose
in terms that are exactly the dossier's: "The Timeline component shows key events relating to a
person or a resource in one place, so your users can see information from a single source of
truth" ([Salesforce — View Events Using Timeline](https://help.salesforce.com/s/articleView?id=ind.timeline.htm&language=en_US&type=5)).
Aqarat's `audit_log` is already this, unrendered.

**"360-degree view" is the marketing term for the whole idea**, and Salesforce uses "single source
of truth" as its companion phrase
([Salesforce — Customer 360 Truth](https://www.salesforce.com/news/press-releases/2019/11/19/salesforce-announces-customer-360-truth-a-single-source-of-truth-for-every-customer-across-the-worlds-1-crm-2/)).
It is a slogan, not a spec, but it is the phrase a reviewer will recognise.

**Property management software confirms the section list from the other side.** Buildium's owner
portal for a property presents financial reports (P&L, contributions and draws, drill-down to
transactions), payments and transaction history, a document-sharing area for "receipts, leases,
and other important items", complete maintenance and repair history, and communications
([Buildium — property owner portal](https://www.buildium.com/features/property-owner-portal/)).
Buildium's help centre describes a per-property **Financials** page reaching the general ledger
and a **Documents** page showing "all files that have been shared for the rental property"
(*snippet* — help.buildium.com is Salesforce-hosted and does not render for automated fetching;
the same limitation `marketplace-domain-research.md` records for Zendesk-hosted help centres).
AppFolio's equivalent is not verified first-party — **unverified**.

**The common ordering, across all four products.** Identity first, lifecycle second, then the
things that happen to the record, then the paperwork, then the history:

1. **Identity / highlights** — what this record is, in one strip. Salesforce's Highlights Panel;
   HubSpot's left sidebar property cards.
2. **Lifecycle / stage** — Salesforce's Path component. Aqarat has this already as
   `UIHelper.createLifecycleBar(status)`.
3. **Details** — the full field set.
4. **Related records** — the associated objects. In a property's case: viewings, reservations,
   contracts, payments.
5. **Documents / attachments** — HubSpot's right sidebar, Buildium's Documents page.
6. **Activity / audit timeline** — chronological, last, and read-only.

Two design points worth stealing outright. **Attachments are a peer of the record, not a footnote** —
both HubSpot and Buildium surface them at the top level. And **the timeline is a merge of several
sources into one chronology**, which is exactly the `audit_log` merge problem noted in §1.5.

# 3. Synthesis

## 3.1 Recommended `property_document` table

Written in the style of `db/schema.sql` — aligned columns, named constraints, comments explaining
*why*.

```sql
/* --------------------------------------------------------------------------
   Private ownership documents

   The paperwork behind a listing: title deed, national ID, agency mandate,
   power of attorney, inheritance decision. Deliberately NOT property_photo:
   photos are public and are what a guest browses, these are private and are
   seen only by the uploading owner and by staff.

   file_path is relative to the uploads root, the same convention
   property_photo uses (PhotoStore). The path is a location, not an access
   control - the application's permission check governs the application, and
   nothing stops someone reading uploads/documents/ directly. That limitation
   is documented in the README rather than papered over.
   -------------------------------------------------------------------------- */

CREATE TABLE dbo.property_document (
    id             INT IDENTITY(1,1) NOT NULL,
    property_id    INT           NOT NULL,
    uploaded_by    INT           NOT NULL,
    document_type  VARCHAR(20)   NOT NULL,
    file_path      VARCHAR(300)  NOT NULL,
    original_name  VARCHAR(200)  NOT NULL,
    file_size      INT           NOT NULL,
    note           VARCHAR(300)  NULL,
    verified_by    INT           NULL,
    verified_at    DATETIME2(0)  NULL,
    verify_note    VARCHAR(300)  NULL,
    uploaded_at    DATETIME2(0)  NOT NULL CONSTRAINT df_doc_uploaded DEFAULT SYSUTCDATETIME(),

    CONSTRAINT pk_property_document PRIMARY KEY (id),
    CONSTRAINT fk_doc_property   FOREIGN KEY (property_id) REFERENCES dbo.property(id)
        ON DELETE CASCADE,
    CONSTRAINT fk_doc_uploader   FOREIGN KEY (uploaded_by) REFERENCES dbo.app_user(id),
    CONSTRAINT fk_doc_verifier   FOREIGN KEY (verified_by) REFERENCES dbo.app_user(id),

    CONSTRAINT ck_doc_type CHECK (document_type IN
        ('TITLE_DEED','NATIONAL_ID','AGENCY_MANDATE','POWER_OF_ATTORNEY',
         'INHERITANCE_DEED','OTHER')),
    CONSTRAINT ck_doc_size CHECK (file_size > 0),

    /* A verification is a person and a moment together. Recording one without
       the other produces a row that cannot answer "who said this was valid",
       which is the only question the column exists to answer. */
    CONSTRAINT ck_doc_verified CHECK (
        (verified_by IS NULL     AND verified_at IS NULL)
     OR (verified_by IS NOT NULL AND verified_at IS NOT NULL))
);
GO

CREATE INDEX ix_document_property ON dbo.property_document(property_id, uploaded_at);
GO
```

Column by column:

| Column | Why |
|---|---|
| `property_id` | The key everything in the dossier already hangs off. `ON DELETE CASCADE` matches `property_photo` (`schema.sql:155`) and `valuation` (`:181`) — the same cascade rule, so it is not a new idea. |
| `uploaded_by` | Not derivable from `property.owner_id`: an agent may upload a mandate on the owner's behalf, and the audit story needs to know which. |
| `document_type` | `VARCHAR(20)` with a `CHECK`, matching the Java enum name for name — the pattern `DESIGN.md` §8 fixes for every status column. 20 is the longest constant (`POWER_OF_ATTORNEY` is 17) with room. |
| `file_path` | `VARCHAR(300)`, identical to `property_photo.file_path` (`schema.sql:149`) and `payment.proof_path` (`:298`). Relative to the uploads root. |
| `original_name` | The name the owner's file had, kept so the UI can say "deed-scan-2024.pdf" instead of "d42-0.pdf". **Stored as data and rendered as a label — never used to build a path.** That distinction is the whole of §2.3. |
| `file_size` | Bytes. Lets the list show a size without touching the disk, and makes a missing or truncated file detectable by comparison. |
| `note` | The owner's own line — "deed is in my late father's name, see the inheritance decision". Free text, optional. |
| `verified_by` / `verified_at` | The §2.4 requirement, and the only reason the table is more than a path. The verification outlives the file: delete the bytes and this row still says who checked, and when. |
| `verify_note` | Why the agent accepted or queried it. Without it, `verified_by` records that a decision happened but not what it was. |
| `uploaded_at` | `DATETIME2(0) DEFAULT SYSUTCDATETIME()`, the pattern every other table uses. UTC in, `Format.dateTime` out. |

**Deliberately absent, with reasons:**

- **No `is_verified BIT`.** `verified_at IS NOT NULL` already answers it, and a second source of
  truth for the same fact is the classic way to get a row where the two disagree.
- **No `status` enum on the document** (`PENDING`/`VERIFIED`/`REJECTED`). Tempting, and wrong at
  this size — it would be a third state machine in a system that already has ten enums, to express
  something two nullable columns and a note express. Add it if a rejected document ever needs to
  behave differently from an unverified one; it does not today.
- **No `varbinary(max)` column.** §2.2.
- **No deed field breakdown** (`deed_number`, `registry_office`, parcel key parts).
  `marketplace-domain-research.md` §1.6 makes a good case that these belong on `property` as
  *fields* — but that is a change to `property`, a shared-surface table, for a different feature.
  Keep the two separate: this table stores the file, that change stores the reference.
- **No `property_owner` table with shares.** Section 2.1 confirms co-ownership is normal and
  `marketplace-domain-research.md` §1.6 already lists it as NICE-TO-HAVE. It is a schema change
  that touches every property query. Out of scope, correctly.
- **No table for the dossier.** It aggregates rows that already key on `property_id`. A new table
  would be a cache of things the database can already answer.

**The permission check, concretely.** One service method, and the shape is what makes it safe:

```java
// Private paperwork: only the owner of the property and staff ever see it.
// The requesting user picks the query rather than filtering its result, so
// there is no path through this method that returns another owner's
// documents (DESIGN.md section 8, the same rule as ContractService.findByClient).
public List<PropertyDocument> findDocuments(int propertyId, AppUser requester)
        throws SQLException, NotPermittedException {
    if (requester == null) {
        throw new NotPermittedException("Sign in to view ownership documents.");
    }
    try (Connection connection = Db.get()) {
        if (requester.getRole() == Role.AGENT || requester.getRole() == Role.ADMIN) {
            return documentDao.findByProperty(connection, propertyId);
        }
        // A customer gets the owner-scoped query. Their own id is bound into
        // the WHERE clause, so a customer who is not the owner gets an empty
        // list from the database rather than a filtered one from Java.
        return documentDao.findByPropertyForOwner(connection, propertyId, requester.getId());
    }
}
```

with the DAO's owner query being:

```sql
SELECT d.id, d.property_id, d.uploaded_by, d.document_type, d.file_path, ...
FROM property_document d
JOIN property p ON p.id = d.property_id
WHERE d.property_id = ? AND p.owner_id = ?
ORDER BY d.uploaded_at
```

Three things this gets right that the current pattern does not. It takes the **user**, not an id,
so a caller cannot pass someone else's. The customer branch **binds the owner id into SQL** rather
than filtering afterwards, which is the rule `DESIGN.md` §8 states and `ContractDao.java:95-97`
comments. And the guest case throws rather than returning an empty list, so "nothing here" and
"not allowed" are distinguishable.

The controller still gates the *panel* by role, as `MyContractsController.java:85-89` does. Both
layers, as today — the service check is the one that cannot be bypassed.

## 3.4 MUST-HAVE / NICE-TO-HAVE / OUT-OF-SCOPE

**MUST-HAVE**

- `property_document` as specified, with `verified_by` / `verified_at`. The verification pair is
  the feature; without it this is a file-attachment widget.
- `DocumentType` matching in all three places — `CHECK`, Java enum, seed data.
- `DocumentStore` mirroring `PhotoStore`, with a **generated** filename. The single most valuable
  security property in Feature A and it is free (§2.3).
- Extension allow-list `{jpg, jpeg, png, pdf}` and a size cap. Two conditions.
- The owner-or-staff check in the **service**, taking the `AppUser` and binding the owner id into
  SQL (§3.3).
- The dossier panel with all ten sections, each with an empty state and a failure state.
- The three service methods and one DAO overload the dossier needs (§1.5) — 20 lines total.
- One honest README paragraph: documents are on the local filesystem; the permission check governs
  the application only; a production system would move them behind a service or into the database.

**NICE-TO-HAVE**

- Magic-byte sniffing on top of the extension check. ~15 lines, and it is the difference between
  "we check the extension" and "we check the file". Do it if Feature A lands early.
- A staff **delete** for a verified document, leaving the verification row. The honest, cheap
  version of retention (§2.4).
- Merging the audit timeline across `property`, `contract`, `payment`, `viewing` and `reservation`
  entity types rather than showing only `"property"`. A `Comparator` and a merged list.
- One `Task` gathering the dossier's queries off the FX thread with a spinner, as `UI-STYLE.md`
  §5H asks. The dossier is the panel where synchronous loading is most likely to show (§1.6).
- Deed reference fields (`deed_number`, `registry_office`, parcel key) on `property`. Already
  flagged in `marketplace-domain-research.md` §1.6 and genuinely cheap — but it touches a
  shared-surface table for a different reason, so it is its own change.
- Reading `storage.images` / `storage.proofs` from `Config` instead of hardcoding `"uploads"` in
  six places (§1.1), and adding `storage.documents`. A tidy-up, not a feature.

**OUT-OF-SCOPE, AND THAT IS CORRECT**

- `varbinary(max)`, FILESTREAM or FileTable. §2.2. FILESTREAM in particular breaks the two-minute
  setup `DECISIONS.md` §12 was written to protect.
- Encryption at rest, NTFS ACLs, or any real access control over the folder. Document the
  limitation instead.
- A retention scheduler or automatic deletion after N days. `DECISIONS.md` §19: nothing in this
  system runs on a timer, and that decision was made twice already.
- OCR or automated field extraction from a deed. `marketplace-domain-research.md` §1.6 already
  refuses this: "Say 'an agent reads it' and move on."
- Any land-registry integration. There is no public API to call.
- Document versioning, e-signature, or a `property_owner` shares table.
- A `document_status` enum. §3.1.
- A new `Panel` in the sidebar for the dossier. It is reached from a property, which is what makes
  it a dossier rather than a report.
- Editing anything from the dossier. It is a case file. The moment it has a Save button it is a
  second editor for records that already have one, and the two will disagree.
